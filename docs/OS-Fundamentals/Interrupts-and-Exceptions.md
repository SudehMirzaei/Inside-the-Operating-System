# Interrupts and Exceptions

## Introduction

Interrupts and exceptions are the fundamental mechanisms that allow the CPU to respond to events—both external (hardware devices) and internal (program errors or special conditions). They are the foundation of preemptive multitasking, efficient I/O handling, and system calls. Without interrupts, a CPU would have to constantly poll devices to see if they need attention, wasting enormous amounts of processing time. Without exceptions, errors like division by zero or invalid memory access would go undetected, leading to silent corruption or undefined behavior.

This document explores interrupts and exceptions in depth: what they are, how they work, how the CPU and OS handle them, and why they're essential to modern computing.

---

## What Are Interrupts and Exceptions?

### The Basic Concept

An interrupt is a signal that causes the CPU to pause its current execution, save its state, and transfer control to a special routine called an interrupt handler (or interrupt service routine, ISR). After the handler finishes, the CPU resumes the interrupted program.

An exception is similar but is triggered by the CPU itself in response to an instruction that cannot complete normally (e.g., division by zero, page fault, invalid opcode).

```
Interrupt/Exception Concept:

Normal Execution:
    ┌─────────────────────────────────────────┐
    │  Instruction 1 → Instruction 2 → ...    │
    └─────────────────────────────────────────┘

With Interrupt/Exception:
    ┌─────────────────────────────────────────┐
    │  Instruction 1 → [EVENT] → Handler →    │
    │  Resume Instruction 2 → ...             │
    └─────────────────────────────────────────┘
```

### Key Terminology

| Term                         | Definition                                             |
|------------------------------|-------------------------------------------------------|
| Interrupt                    | Asynchronous signal from hardware or software         |
| Exception                    | Synchronous event caused by an instruction            |
| Interrupt Handler (ISR)      | Code that runs in response to an interrupt            |
| Interrupt Vector             | Index into the interrupt vector table                  |
| Interrupt Vector Table (IVT/IDT) | Array of handler addresses                       |
| Interrupt Latency            | Time from interrupt signal to handler start           |
| Maskable Interrupt           | Can be temporarily disabled                            |
| Non-Maskable Interrupt (NMI) | Cannot be disabled                                     |

## Types of Events

### 1. Hardware Interrupts (Asynchronous)

Generated by external hardware devices at unpredictable times:

```
Hardware Interrupt Sources:

├── Timer
│   ├── Periodic tick for scheduling
│   ├── System timekeeping
│   ├── Watchdog timer
│   └── Example: Programmable Interval Timer (PIT)

├── I/O Devices
│   ├── Disk controller (I/O completion)
│   ├── Network card (packet received)
│   ├── Keyboard (key pressed)
│   ├── Mouse (moved or clicked)
│   ├── USB device (plugged in)
│   └── Sound card (buffer empty)

├── Inter-Processor Interrupts (IPIs)
│   ├── CPU to CPU communication
│   ├── TLB shootdown
│   ├── Rescheduling
│   ├── System-wide operations
│   └── Multiprocessor coordination

└── Power Events
    ├── Power button pressed
    ├── Battery low
    ├── Thermal warning
    └── Power failure

Characteristics:
├── Asynchronous (occur any time)
├── External to CPU
├── Not related to current instruction
├── Can be masked (usually)
└── Handled by OS
```

### 2. Software Interrupts (Synchronous)

Generated by executing specific instructions:

```
Software Interrupts:

├── System Calls
│   ├── User program requests OS service
│   ├── Uses trap instruction (INT, SYSCALL)
│   ├── Deliberate, controlled
│   ├── Well-defined entry point
│   └── Example: write(), fork()

├── Breakpoints
│   ├── INT 3 instruction (x86)
│   ├── Used by debuggers
│   ├── Pauses execution
│   ├── Returns control to debugger
│   └── Part of debugging process

├── Inter-Processor Interrupts (IPIs)
│   ├── Can be triggered by software
│   ├── Send signals between CPUs
│   ├── Used for TLB shootdown
│   └── Coordination in SMP systems

Characteristics:
├── Synchronous (tied to instruction)
├── Intentional (program initiated)
├── Well-defined entry points
├── Controlled mechanism
└── Used for system calls
```

### 3. Exceptions (Synchronous)

Triggered by the CPU in response to instruction execution issues:

```
Exception Types:

1. Faults
   ├── Correctable exceptions
   ├── Instruction can be re-executed
   ├── Program may continue after handler
   ├── Example: Page fault (memory not present)
   └── Handler fixes issue, retries instruction

2. Traps
   ├── Intentional exceptions
   ├── Reported after instruction
   ├── Program continues after handler
   ├── Example: Breakpoint, overflow
   └── Used for debugging, system calls

3. Aborts
   ├── Unrecoverable exceptions
   ├── Program cannot continue
   ├── Often indicates hardware or severe software error
   ├── Example: Machine check, bus error
   └── Usually terminates process

Common Exceptions:

Page Fault:
├── Type: Fault
├── Cause: Memory page not in RAM
├── Handler: Load page from disk
├── Result: Instruction retried
└── Common, normal operation

Divide by Zero:
├── Type: Fault (or trap)
├── Cause: Division by zero
├── Handler: Signal to process (SIGFPE)
├── Result: Usually terminate process
└── Program error

General Protection Fault:
├── Type: Fault
├── Cause: Privilege violation or memory access
├── Handler: Check what happened
├── Result: Usually terminate process
└── Security protection

Invalid Opcode:
├── Type: Fault
├── Cause: Undefined instruction
├── Handler: Signal to process (SIGILL)
├── Result: Terminate process
└── Programming error

Debug Exception:
├── Type: Trap or fault
├── Cause: Breakpoint or single-step
├── Handler: Give control to debugger
├── Result: Debugger inspects state
└── Debugging support

Overflow:
├── Type: Trap
├── Cause: Arithmetic overflow
├── Handler: Signal to process (SIGSEGV or ignored)
├── Result: Depends on program
└── Optional checking
```

### Comparison Table

| Event Source                 | Sync? | Predictable? | Recoverable? |
|------------------------------|-------|--------------|---------------|
| Hardware Interrupt            | No    | No           | Yes           |
| Software Interrupt            | Yes   | Yes          | Yes           |
| Fault                         | Yes   | Yes          | Usually       |
| Trap                          | Yes   | Yes          | Yes           |
| Abort                         | Yes   | Depends      | No            |

## Interrupt Hardware

### The Interrupt Controller

Hardware manages interrupt signals before they reach the CPU:

```
Interrupt Flow:

Device → Interrupt Controller → CPU

Traditional (PIC - Programmable Interrupt Controller):
├── Intel 8259A (legacy)
├── Two cascaded controllers (16 IRQs)
├── IRQ 0-15
├── Limited number of interrupts
├── Fixed priority
└── Obsolete but historically important

Modern (APIC - Advanced Programmable Interrupt Controller):
├── Local APIC (per CPU)
├── I/O APIC (system-wide)
├── More interrupts (24+ typically)
├── Better priority management
├── Multiprocessor support
├── Inter-Processor Interrupts (IPIs)
└── Standard on modern systems

APIC Architecture:
┌─────────────────────────────────────────────┐
│  CPU 0                    CPU 1             │
│  ┌─────────┐              ┌─────────┐       │
│  │Local    │              │Local    │       │
│  │APIC     │              │APIC     │       │
│  └────┬────┘              └────┬────┘       │
│       │                        │            │
│       └────────────┬───────────┘            │
│                    │                        │
│              ┌─────┴─────┐                  │
│              │  I/O APIC │                  │
│              └─────┬─────┘                  │
│                    │                        │
│       ┌────────────┼────────────┐           │
│       │            │            │           │
│   ┌───┴───┐   ┌───┴───┐   ┌───┴───┐        │
│   │Disk   │   │Network│   │Keyboard│        │
│   └───────┘   └───────┘   └───────┘        │
└─────────────────────────────────────────────┘
```

### Interrupt Lines

Each device is connected to an interrupt line:

```
Interrupt Line Concept:

Device            Line     Vector    Priority
─────────────────────────────────────────────
Timer             IRQ 0     32       Highest
Keyboard          IRQ 1     33       High
Cascade           IRQ 2     34       (for old PIC)
Serial Port 1     IRQ 4     36       Medium
Serial Port 2     IRQ 3     35       Medium
Parallel Port     IRQ 7     39       Low
RTC               IRQ 8     40       Medium
USB               IRQ 11    43       Medium
Network           IRQ 11    43       Medium
Disk              IRQ 14    46       Medium

Modern systems:
├── Interrupts assigned dynamically
├── APIC handles routing
├── MSI (Message Signaled Interrupts)
├── MSI-X (extended)
└── No fixed IRQ assignment
```

### Message Signaled Interrupts (MSI)

Modern devices use MSI instead of dedicated interrupt lines:

```
MSI (Message Signaled Interrupts):

Traditional Interrupts:
├── Dedicated interrupt line per device
├── Limited number of lines
├── Shared lines problematic
├── IRQ assignment conflicts
└── Physical wires required

MSI:
├── Device writes to special memory address
├── Message routed to CPU
├── No physical interrupt line
├── Multiple interrupts per device
├── Better performance
└── PCIe feature

MSI-X:
├── Extended MSI
├── Up to 2048 vectors per device
├── Per-queue interrupts
├── Better for multi-queue devices
├── Common for network cards
└── Standard for high-performance I/O

Benefits:
├── No IRQ sharing issues
├── Better interrupt affinity
├── Reduced latency
├── More interrupts per device
└── Better performance
```

### Interrupt Priority

Interrupts have priorities that determine handling order:

```
Interrupt Priority Levels:

x86 Priority:
1. Hardware Reset (highest)
2. Machine Check
3. NMI (Non-Maskable Interrupt)
4. Breakpoint
5. Overflow
6. Debug
7. Software Interrupts (INT n)
8. External Interrupts (IRQ)
   ├── Higher priority handled first
   ├── Lower priority may be delayed
   └── Can be masked

Priority Handling:
├── Higher priority preempts lower
├── Lower priority waits
├── Same priority queued
├── NMI cannot be masked
└── Priority managed by APIC

Linux Priority Assignment:
├── NMI: Highest
├── IRQ 0 (timer): Very high
├── Device interrupts: Various
├── Softirqs: Lower priority
├── Tasklets: Even lower
├── Workqueues: Lowest (kernel threads)
└── User processes: Normal
```

## Interrupt Handling

### The Interrupt Vector Table

The CPU uses a table to find the correct handler:

```
Interrupt Vector Table (IDT on x86-64):

Interrupt  Vector  Purpose
──────────────────────────────────────
0          0       Divide by zero
1          1       Debug
2          2       NMI
3          3       Breakpoint
4          4       Overflow
5          5       Bounds check
6          6       Invalid opcode
7          7       Device not available
8          8       Double fault
9          9       Coprocessor segment
10         10      Invalid TSS
11         11      Segment not present
12         12      Stack fault
13         13      General protection
14         14      Page fault
15         15      Reserved
16         16      x87 FPU error
17         17      Alignment check
18         18      Machine check
19         19      SIMD FPU error
20-31      20-31   Reserved
32-47      32-47   Hardware IRQs
48-255     48-255  Software interrupts / syscalls

IDT Structure (x86-64):
├── 256 entries
├── Each entry: 16 bytes
│   ├── Handler address (64 bits)
│   ├── Segment selector
│   ├── Type/attributes
│   └── IST (Interrupt Stack Table)
├── Base address in IDTR register
└── Loaded by OS during boot

Handler Lookup:
1. Interrupt occurs
2. CPU reads interrupt number
3. Look up IDT entry
4. Get handler address
5. Save state
6. Jump to handler
```

### The Interrupt Handling Process

```
Interrupt Handling Steps:

1. Interrupt Detected
   ├── Signal on interrupt line
   ├── Or software INT instruction
   ├── Or exception condition
   └── CPU acknowledges interrupt

2. Save Context (Hardware)
   ├── Push flags register
   ├── Push CS (code segment)
   ├── Push RIP (instruction pointer)
   ├── Push SS (stack segment) - if privilege change
   ├── Push RSP (stack pointer) - if privilege change
   └── Minimal state saved by hardware

3. Switch Stacks (if needed)
   ├── User → kernel: switch to kernel stack
   ├── Kernel → kernel: continue on current stack
   ├── Uses TSS (Task State Segment) on x86
   ├── Essential for security
   └── Prevents user stack manipulation

4. Look Up Handler
   ├── Read IDT entry for interrupt number
   ├── Get handler address
   └── Validate entry

5. Execute Handler
   ├── Save additional registers (software)
   ├── Process the interrupt
   ├── Do minimal work
   ├── Schedule deferred work
   └── Send EOI to interrupt controller

6. Restore Context
   ├── Restore registers
   ├── Execute IRET instruction
   ├── IRET pops flags, CS, RIP
   ├── Switch back to user stack (if needed)
   └── Resume interrupted code
```

### The Interrupt Stack

Each privilege level has its own stack:

```
Interrupt Stack Switching:

User Mode → Kernel Mode (interrupt):
├── CPU switches to kernel stack
├── Uses TSS to find kernel stack
├── Saves user context on kernel stack
├── Kernel handler runs on kernel stack
└── IRET returns to user stack

Kernel Mode → Kernel Mode (interrupt):
├── Continue on current kernel stack
├── No stack switch needed
├── Already in kernel
└── May need to check stack depth

Interrupt Stack Contents:
┌─────────────────────────────────┐
│  User SS                        │  ← Pushed by hardware
│  User RSP                       │
│  User RFLAGS                    │
│  User CS                        │
│  User RIP                       │
├─────────────────────────────────┤
│  Error code (if applicable)     │  ← Pushed by hardware
├─────────────────────────────────┤
│  Saved registers               │  ← Pushed by software
│  (RAX, RBX, RCX, ...)          │
├─────────────────────────────────┤
│  Local variables               │
│  Kernel function frames        │
├─────────────────────────────────┤
│  Interrupt handler code        │
│  running here                  │
└─────────────────────────────────┘

Why Separate Stacks:
├── Security: user can't manipulate kernel stack
├── Reliability: kernel stack always valid
├── Correctness: independent of user state
├── Recovery: can handle user stack faults
└── Foundation of protection
```

### Interrupt Masking

Interrupts can be temporarily disabled:

```
Interrupt Masking:

Why Mask:
├── Protect critical sections
├── Prevent race conditions
├── Ensure atomic operations
├── Modify interrupt-related data safely
└── Short critical sections only

CLI/STI (x86):
├── CLI: Clear Interrupt Flag (disable)
├── STI: Set Interrupt Flag (enable)
├── Affects maskable interrupts
├── NMI unaffected
├── Used in kernel critical sections

Example (simplified):
// Disable interrupts
cli();

// Critical section - no interrupts
update_shared_data();
update_pointer();

// Re-enable interrupts
sti();

Masking Levels:
├── Individual interrupt masking (APIC)
│   ├── Mask specific IRQ line
│   ├── Other interrupts continue
│   └── Fine-grained control
│
├── Global interrupt masking (CLI)
│   ├── Mask all maskable interrupts
│   ├── Used for short critical sections
│   ├── Should be brief
│   └── Latency concern

├── NMI (Non-Maskable Interrupt)
│   ├── Cannot be masked
│   ├── For critical events
│   ├── Hardware errors
│   ├── Watchdog timeouts
│   └── Emergency situations

Best Practices:
├── Minimize masking time
├── Use spinlocks instead where possible
├── Keep critical sections short
├── Avoid calling functions that sleep
├── Consider interrupt latency
└── Use appropriate primitives
```

## Interrupt Latency and Overhead

### Interrupt Latency

Interrupt latency is the time from when an interrupt is signaled to when the handler begins executing:

```
Interrupt Latency Components:

Total Latency = Hardware + Software + Queueing

1. Hardware Latency
   ├── Signal propagation
   ├── Interrupt controller processing
   ├── CPU acknowledgment
   ├── Context save (hardware)
   ├── Vector lookup
   └── Typically: few hundred ns

2. Software Latency
   ├── Time interrupts are disabled
   ├── Critical sections
   ├── Higher priority handlers
   ├── Kernel preemption disabled
   └── Variable: microseconds to milliseconds

3. Queueing Latency
   ├── Waiting for CPU
   ├── Higher priority interrupts
   ├── Scheduler decisions
   ├── Processor availability
   └── Variable

Typical Latencies:
├── Hardware: 100-500 ns
├── Simple handler start: ~1 μs
├── With disabled interrupts: varies
├── Worst case (real-time): bounded
├── Standard Linux: ms range
└── RT Linux: < 100 μs

Real-Time Systems:
├── Bounded latency required
├── Predictable behavior
├── Maximum latency specified
├── PREEMPT_RT Linux: < 100 μs
├── VxWorks: < 10 μs
└── QNX: < 5 μs
```

### Interrupt Overhead

```
Interrupt Overhead:

Cost of Interrupt Handling:
├── Context save/restore: ~100-500 cycles
├── Handler execution: variable
├── Cache effects: significant
├── Pipeline flush: ~20-50 cycles
├── TLB effects: possible
└── Total: microseconds per interrupt

Comparison:
├── Interrupt: ~1-10 μs
├── Function call: ~1-10 ns
├── Ratio: 100-1000x
└── Minimize interrupts when possible

High Interrupt Rates:
├── Network cards: 100,000+ interrupts/sec
├── High-performance storage: many
├── Timer interrupts: 100-1000/sec
├── Overhead can be significant
└── Solutions: NAPI, MSI-X, interrupt coalescing

Optimization Techniques:
├── Interrupt coalescing
│   ├── Batch multiple interrupts
│   ├── Reduce interrupt rate
│   ├── Better efficiency
│   └── Slight latency increase
│
├── NAPI (Linux networking)
│   ├── Hybrid interrupt/polling
│   ├── Poll under high load
│   ├── Reduce interrupt overhead
│   └── Better throughput
│
├── MSI-X
│   ├── Multiple interrupt vectors
│   ├── Per-queue interrupts
│   ├── Better CPU affinity
│   └── Parallel processing
│
└── Deferred processing
    ├── Minimal work in handler
    ├── Defer rest to softirq/tasklet
    ├── Enable interrupts sooner
    └── Better system responsiveness
```

## Deferred Processing

Because interrupt handlers should be fast, work is often deferred:

### Top Half vs. Bottom Half

```
Interrupt Handler Split:

Top Half (Hard Interrupt Context):
├── Runs immediately on interrupt
├── Interrupts disabled (usually)
├── Must be very fast
├── Cannot sleep
├── Minimal processing
├── Acknowledge interrupt
├── Save data
├── Schedule bottom half
└── Return quickly

Bottom Half (Soft Interrupt Context):
├── Runs later
├── Interrupts enabled
├── Can take more time
├── Still cannot sleep (usually)
├── Process saved data
├── Complete work
├── More complex processing
└── Multiple mechanisms

Timeline:
Interrupt ──┐
            │
            ▼
    ┌───────────────┐
    │ Top Half      │  Fast, minimal
    │ (hard IRQ)    │  Interrupts off
    └───────┬───────┘
            │
            ▼
    ┌───────────────┐
    │ Bottom Half   │  Later, more work
    │ (softirq)     │  Interrupts on
    └───────────────┘

Benefits:
├── Fast interrupt handling
├── Better system responsiveness
├── Reduced interrupt latency
├── More work per interrupt
└── Flexible processing
```

### Bottom Half Mechanisms (Linux)

```
Linux Deferred Processing:

1. Softirqs
   ├── Statically defined
   ├── Limited number (currently 10)
   ├── Run on same CPU
   ├── Can run in parallel (same type)
   ├── High priority
   ├── Examples: network, block I/O
   └── Cannot sleep

2. Tasklets
   ├── Built on softirqs
   ├── Dynamic (can be created)
   ├── Run on same CPU
   ├── Serialized (one at a time)
   ├── Lower priority than softirqs
   ├── Cannot sleep
   └── Being deprecated in favor of threaded IRQs

3. Workqueues
   ├── Run in kernel thread context
   ├── Can sleep
   ├── Can block
   ├── Longer operations
   ├── Lower priority
   └── Examples: filesystem operations

4. Threaded IRQs
   ├── Run in dedicated kernel thread
   ├── Can sleep
   ├── Can be prioritized
   ├── Modern approach (PREEMPT_RT)
   ├── Better for real-time
   └── Preferred in modern Linux

Priority Order:
├── Hard IRQ (highest)
├── Softirq
├── Tasklet
├── Threaded IRQ
├── Workqueue
└── User processes (lowest)
```

### Choosing a Mechanism

```
When to Use Each Mechanism:

Hard IRQ Top Half:
├── Acknowledge hardware
├── Read critical data
├── Schedule bottom half
├── Always minimal
└── Cannot sleep or block

Softirq:
├── High-frequency processing
├── Network stack
├── Block I/O completion
├── Time-critical operations
├── Parallelizable work
└── No sleeping

Tasklet:
├── Medium-frequency processing
├── Driver bottom halves
├── Serialized operations
├── Prefer threaded IRQ now
└── No sleeping

Threaded IRQ:
├── Most driver work
├── Operations that might sleep
├── Real-time systems
├── Priority control needed
├── Can sleep and block
└── Modern preferred approach

Workqueue:
├── Long-running operations
├── Can sleep freely
├── Filesystem work
├── Deferred tasks
├── Lower priority
└── Flexible scheduling
```

## Common Misconceptions

**Misconception 1**: "Interrupts are always bad for performance"

**Reality**: Interrupts are essential for efficient I/O. Without them, the CPU would waste time polling devices. Interrupts enable the CPU to do other work while waiting for I/O completion. The overhead is offset by the benefits.

**Misconception 2**: "Interrupts are just function calls"

**Reality**: Interrupts involve hardware context save, potentially stack switching, and mode changes. They're much more expensive than function calls—typically 100-1000x more. This is why interrupt minimization is important.

**Misconception 3**: "Exception handlers always terminate the program"

**Reality**: Many exceptions are recoverable. Page faults are exceptions that occur constantly and are handled transparently. The OS loads the page and retries the instruction. Only unrecoverable exceptions terminate processes.

**Misconception 4**: "Interrupts can happen at any instruction boundary"

**Reality**: While interrupts are asynchronous, the CPU checks for them at specific points—typically between instructions. Some instructions are atomic and won't be interrupted. The exact behavior is architecture-specific.

**Misconception 5**: "You should do as much work as possible in the interrupt handler"

**Reality**: You should do as little work as possible in the interrupt handler. Long handlers block other interrupts and degrade responsiveness. Work should be deferred to bottom halves.

**Misconception 6**: "NMI means the system always crashes"

**Reality**: NMIs are used for critical events like hardware errors, but not all NMIs are fatal. Watchdog timers use NMIs, and they can be handled gracefully. NMI handling depends on the cause.

**Misconception 7**: "Disabling interrupts is always dangerous"

**Reality**: Disabling interrupts briefly is a legitimate technique for protecting critical sections. The danger is long interrupt-disabled regions, which increase latency. Short, controlled masking is normal and necessary.

## Summary

Interrupts and exceptions are essential mechanisms that enable the CPU to respond to hardware events, software requests, and error conditions. Interrupts are asynchronous signals from hardware devices; exceptions are synchronous events caused by instruction execution. Both transfer control to handlers via the interrupt vector table, using separate kernel stacks for security and reliability.

### Key Points

1. Interrupts are asynchronous — hardware events occurring any time.
2. Exceptions are synchronous — caused by instruction execution.
3. The IDT/IVT maps interrupt numbers to handler addresses.
4. Context is saved — hardware saves minimal state; software saves more.
5. Stack switching — kernel stack used for handling.
6. Top half / bottom half — split handling for responsiveness.
7. Interrupts enable preemption — timer interrupts drive scheduling.
8. System calls use interrupts — INT or SYSCALL instructions.

---

## Key Takeaways

1. Interrupts make computing efficient — no need to poll devices.
2. Exceptions handle errors — faults, traps, and aborts.
3. Context save/restore is essential — CPU must resume correctly.
4. Separate stacks provide security — user can't manipulate kernel.
5. Deferred processing is critical — keep handlers short.
6. Masking has consequences — increases latency, use carefully.
7. Multiprocessor systems need IPIs — CPU coordination requires interrupts.
8. Real-time systems bound latency — predictability is paramount.
